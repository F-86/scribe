# 设计文档 / 架构文档编写指南

## 定位

设计文档回答一个问题:**这个系统为什么长这样?** 读者是贡献者(含未来的自己),他们要改代码、扩功能,需要先理解模块怎么划分、数据怎么流动、关键取舍是怎么定的。

它不是 README(怎么用),也不是 ADR(单个决策的始末)。见 [`doc-map.md`](doc-map.md):**设计文档描述整体架构现状,ADR 记录单个决策始末**;一份设计文档背后通常有多条 ADR 支撑。

设计文档有两种典型场景,动笔前先确认:

| 场景 | 信号 | 时态 |
|------|------|------|
| **现状架构文档** | "架构文档"、"系统设计"、"整体设计"、"模块说明" | 描述已建成的系统 |
| **方案设计 / RFC** | "设计方案"、"RFC"、"技术方案"、"提案" | 描述拟议的改动,待评审 |

## 结构模板

### 现状架构文档

```markdown
# {系统名} 架构设计

## 概述
一段话讲清:这个系统解决什么问题、核心思路是什么。

## 目标与非目标
- **目标**:系统要达成的能力(可衡量)
- **非目标**:明确不解决的问题,划定边界

## 整体架构
<架构图:模块框图 / 数据流图,用 mermaid 绘制>

各模块职责:
| 模块 | 职责 | 依赖 |
|------|------|------|
| API 层 | 接收请求、鉴权、参数校验 | 服务层 |
| 服务层 | 业务逻辑编排 | 数据层、外部服务 |
| 数据层 | 持久化、缓存 | 数据库 |

## 关键设计决策
- **为什么用 X 而不是 Y**:一句话结论 + 理由(详细始末见对应 ADR)
- 链接到相关 ADR:见 [ADR-0003](adr/0003-xxx.md)

## 数据模型
核心实体及关系(ER 图或表)。

## 关键流程
挑 1-3 个核心流程,讲清请求如何穿过各模块(时序图或编号步骤)。

## 权衡与已知限制
当前架构的取舍、技术债、已知瓶颈。
```

### 方案设计 / RFC

```markdown
# RFC: {方案名}

> 状态:草稿 / 评审中 / 已接受 / 已实现 · 作者:xxx · 日期:2026-06-18

## 背景与问题
当前是什么状况,为什么需要改。

## 目标与非目标

## 提议方案
具体怎么做,改哪些模块,新增什么。

## 备选方案
考虑过但没选的方案,以及为什么(此处与 ADR 有交集:重大选型应沉淀为 ADR)。

## 影响评估
对现有功能、性能、迁移、向后兼容的影响。

## 未决问题
还没想清楚、需要讨论的点。
```

## 编写原则

### DO ✅

- **先讲"为什么"再讲"怎么做"**:决策背后的约束和目标比方案本身更有价值
- 用图说话:模块框图、数据流图、时序图——一张图省千字。**除目录结构(ASCII 树)外,所有图用 mermaid 绘制**(可随代码版本化、自动渲染,见 `general-principles.md` 图表规范)
- 明确**非目标**:划定边界,防止读者误以为系统要解决它不解决的问题
- 重大决策只写结论 + 一句理由,**始末链接到 ADR**,避免设计文档膨胀
- 写已知限制和技术债——诚实的架构文档比粉饰的有用

### DON'T ❌

- 不要把怎么用写进来(那是 README)——设计文档面向"改它的人"
- 不要逐行讲代码——讲结构和意图,代码细节读源码
- 不要写成一次性文档就不维护——架构变了要同步,否则误导比没有更糟;若难维护,标注"截至 vX.Y 的架构"
- 不要把每个决策的完整辩论塞进来——抽成 ADR

## 章节取舍

| 章节 | 何时需要 | 何时可省 |
|------|---------|---------|
| 目标与非目标 | 始终 | 无 |
| 架构图 | 始终 | 无 |
| 数据模型 | 有持久化/复杂数据 | 无状态工具 |
| 关键流程 | 流程复杂 | 单一线性流程 |
| 备选方案 | RFC / 方案设计 | 现状文档(归 ADR) |
| 权衡与限制 | 始终 | 无 |

## 通用规则

- **不虚构架构**:不清楚的模块职责、依赖关系标 `<!-- TODO: 确认 xxx -->`,不臆测
- **优先从已有素材提取**:有代码、目录结构、现有图时从中提取真实结构,不凭空画
- **单一信息源**:决策始末归 ADR,怎么用归 README,设计文档只讲"系统现在是什么样、为什么"
