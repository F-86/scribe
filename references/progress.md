# 项目进度文档(PROGRESS.md)编写指南

## 定位

PROGRESS.md 是一份按阶段组织的待办表,记录**项目要做什么、已经做到哪了**。读者是项目维护者与协作者(包括未来的自己和 AI agent),他们对照它回答:「现在做到哪一步了?下一步做什么?整体分几个阶段?」

推荐文件名 **`PROGRESS.md`**,放项目根目录。也常见 `ROADMAP.md`(偏未来规划/愿景)、`TODO.md`(偏轻量待办)——识别和修改时都按本指南处理。

> **与相邻文档的边界见 [`doc-map.md`](doc-map.md)。** 一句话区分:PROGRESS 朝前看(要做什么、做到哪了),CHANGELOG 朝后看(已发布版本改了什么),README 看当下(这是什么、怎么用)。

## 结构模板(时序阶段制)

```markdown
# 项目进度

> 项目目标:<一句话说清这个项目最终要达成什么>
> 当前阶段:阶段二(进行中) · 最后更新:2026-06-18

## 阶段一:<名称> ✅ 已完成

**目标**:<这一阶段要达成什么,有明确的退出标准>

- [x] 完成的任务 A
- [x] 完成的任务 B

## 阶段二:<名称> 🚧 进行中

**目标**:<本阶段目标>

- [x] 已完成的子任务
- [ ] 进行中的子任务
- [ ] 待开始的子任务

## 阶段三:<名称> ⬜ 待开始

**目标**:<本阶段目标>

- [ ] 计划任务 A
- [ ] 计划任务 B
```

### 状态标记约定

阶段标题用 emoji 标状态,任务用复选框,两者配合:

| 标记 | 含义 | 用在 |
|------|------|------|
| `✅ 已完成` | 阶段全部任务完成 | 阶段标题 |
| `🚧 进行中` | 阶段已开始、未完成 | 阶段标题 |
| `⬜ 待开始` | 阶段尚未启动 | 阶段标题 |
| `- [x]` | 单个任务已完成 | 任务条目 |
| `- [ ]` | 单个任务未完成 | 任务条目 |

不涉及的状态不写。一个阶段标 `🚧` 时,其内部任务应同时有 `[x]` 和 `[ ]`,一眼看出卡在哪。

## 编写原则

### DO ✅

- 每个阶段写明**目标和退出标准**——「阶段二完成」要有可判定的标志,不是模糊的"差不多了"
- 任务粒度可勾选:一条任务能明确判断"做完没有"
- **及时更新状态**:任务做完就勾,阶段完成就改标记。进度文档的价值在于"实时反映现状"
- 顶部标注当前阶段 + 最后更新日期,让读者一眼知道新鲜度
- 阶段按时间顺序排列(阶段一在最上,正在做的在中间,计划在下)

### DON'T ❌

- 不要写成 commit 流水或工时日志——它记"阶段性进展",不记每次提交
- 不要与 CHANGELOG 内容重复:已完成任务只标里程碑,**用户可见的发布变更写进 CHANGELOG**(见 [`doc-map.md`](doc-map.md))
- 不要堆积过期状态:任务做完不勾、阶段完成不更新,文档很快失信
- 不要把无法判定完成的事写成任务条目("优化性能"→改成"首屏加载降到 1s 内")
- 不要一次列出几十个阶段——只规划看得清的近几个阶段,远期用一句话带过

## 章节取舍

| 章节/字段 | 何时需要 | 何时可省 |
|----------|---------|---------|
| 顶部项目目标 | 始终 | 无 |
| 当前阶段 + 更新日期 | 始终 | 无 |
| 阶段目标/退出标准 | 始终 | 无 |
| 任务负责人 | 多人协作 | 单人项目 |
| 关联 issue/PR(`(#123)`) | 用 issue 跟踪的项目 | 无 issue 跟踪 |
| 远期规划区 | 阶段多、跨度长 | 短期小项目 |

## 通用规则

- **不虚构进度**:不确定某任务状态时,标 `<!-- TODO: 确认 xxx 状态 -->`,不臆断已完成
- **优先从已有素材提取**:有 CHANGELOG、issue 列表、看板时,从中提取真实进展,不凭空编阶段
- **单一信息源**:同一件事不在 PROGRESS 和 CHANGELOG 用相同粒度重复描述,各司其职
