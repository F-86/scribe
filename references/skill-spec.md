# Skill 设计规范

## 三层架构

```
L1 — SKILL.md front matter（YAML）
     信号灯：AI 判断"是否触发此 Skill"
     原则：极度精简，≤ 3 行

L2 — SKILL.md body（Markdown 主体）
     操作手册：执行此 Skill 时必然用到的完整内容
     原则：完整、准确，长度不限

L3 — references/ / examples/ / scripts/ / assets/
     知识库：只在特定情境下才会用到的内容
     原则：按需加载
```

**L2 vs L3 的唯一判断标准**：

> 执行此 Skill 时，这段内容**每次都会用到**吗？
> - **是** → 放 L2（SKILL.md 主体）
> - **否，只在某些情境下用到** → 放 L3（references/ 等）

注意：**长度和细节程度不是判断标准**。详细的规则、完整的工具调用格式、参数表格，只要每次执行都需要，就应该在 L2。

**示例**（会议总结 Skill）：
- 摘要格式、待办事项提取规则 → 每次都用 → **L2**
- 资金处理合规要求 → 只有涉及预算的会议才用 → **L3**

## L1 规范：YAML front matter

```yaml
---
name: skill-name        # 必须与文件夹名完全一致
description: >-         # 一句话定位 + 关键词，≤ 1024 字符
  功能描述，说清楚此 Skill 的用途。
  关键词：关键词1、关键词2、关键词3
---
```

**规则**：
- `name` 格式：1-64 字符，仅限小写字母 `a-z`、数字 `0-9`、连字符 `-`，不能以 `-` 开头/结尾，不能包含连续 `--`
- `name` 必须与文件夹名完全一致
- `description` ≤ 3 行且 ≤ 1024 字符：第 1 行核心定位，最后 1 行关键词列表
- 不写触发条件举例、不写执行步骤、不写边界条件——那些属于 L2
- 关键词覆盖用户可能说的自然语言

❌ 反例（L1 过重）：
```yaml
description: >-
  用于数据资产发现。当用户提出以下需求时触发：
  - 模糊搜索表名（"dwd_order 是哪张表"）
  - 查询数据源信息（"数据源 ID 36 是什么"）
  注意：字段血缘请使用 column-explain。
```

✅ 正例：
```yaml
description: >-
  数据资产发现：模糊找表、查数据源连接信息、查表结构和字段。
  关键词：找表、表结构、数据源、字段、连接信息、库表、元数据
```

## L2 规范：SKILL.md 主体

L2 是整个 Skill 的核心。**长度不设上限**，以完整描述执行逻辑为准。

应包含：
- 完整执行流程（步骤顺序、分支决策）
- 工具调用方式（工具名、参数说明、调用示例）
- 核心规则与约束
- 输出格式模板
- L3 文件的加载指针（说明何种情况下参考哪个文件）

### 不适用场景

L2 必须包含一个独立的 **不适用场景** 小节，明确列出不应该使用此 Skill 的情况。
这能大幅降低误触发率，重要性不亚于 L1 的 description。

```markdown
## 不适用场景

- 字段血缘分析 → 请使用 `column-lineage` Skill
- 仅查询单表数据预览 → 直接用 SQL 工具即可，不需要此 Skill
- 数据写入操作 → 此 Skill 只读不写，写入请用 `data-writer`
```

规则：
- 每条说明**什么情况不适用**以及**应该用什么替代**
- 不要只写"其他情况不适用"——必须具体到场景

---

## L3 规范：references/ 等目录

只放**条件性内容**——正常执行路径用不上、只在特定情境触发的内容：

| 内容类型 | 示例 |
|---------|------|
| 特定场景的领域规范 | 涉及资金时的合规要求 |
| 错误排查手册 | 数据库连接失败的诊断步骤 |
| 回滚/应急方案 | 迁移失败时的回滚操作 |
| 触发示例（调试用） | examples/trigger-examples.md |
| 可执行脚本 | scripts/*.py |
| 输出模板文件 | assets/report-template.html |

**不应放 L3 的内容**：
- 每次执行都会用到的工具调用格式
- 核心参数表格（如各数据源的 SQL 格式差异）
- 必经流程中的判断规则

L2 中需要有明确指针，说明何时加载 L3：
```markdown
## 特殊情况处理
- 若检测到 DUMP 父任务，参照 `references/dump-dependency.md`
- 若执行失败需回滚，参照 `references/rollback.md`
```

## 文件夹结构

```
{skill-name}/
├── SKILL.md                  # 必须（L1 + L2）
├── references/               # 按需创建，放条件性知识
│   └── {topic}.md
├── examples/                 # 可选，触发示例（调试用）
├── scripts/                  # 可选，可执行脚本
└── assets/                   # 可选，模板文件
```

---

## 常见错误

| 错误 | 表现 | 修复 |
|------|------|------|
| L1 过重 | description 有多行触发条件或边界条件 | 压缩为一句话 + 关键词 |
| L2 过轻 | SKILL.md 主体只有几行指针，核心逻辑全在 references/ | 把每次必用的内容移回 SKILL.md |
| L2/L3 混淆 | 把"每次必用"的规则放进了 references/ | 移回 SKILL.md 主体 |
| L3 缺失 | L2 里的指针指向不存在的文件 | 创建对应文件 |
| name 不匹配 | front matter 的 name 和文件夹名不同 | 以文件夹名为准 |

---

## 快速检查清单

- [ ] `name` 格式合法（`a-z` `0-9` `-`，1-64 字符）且与文件夹名一致
- [ ] `description` ≤ 3 行且 ≤ 1024 字符，无执行步骤，末行有关键词
- [ ] SKILL.md 主体包含执行时必然用到的完整逻辑
- [ ] L2 包含独立的「不适用场景」小节
- [ ] 只有"条件性内容"放入 references/
- [ ] L2 里对 L3 有明确的加载条件说明

## 完整示例

以下是一个最小但完整的 Skill，演示三层架构的实际落地。

### 文件夹结构

```
meeting-summary/
├── SKILL.md
├── references/
│   └── budget-compliance.md
└── examples/
    └── trigger-examples.md
```

### SKILL.md

```markdown
---
name: meeting-summary
description: >-
  从会议记录中提取摘要、待办事项和关键决策。
  关键词：会议总结、会议纪要、meeting notes、待办、决策
---

# 会议总结

## 执行流程

1. 读取用户提供的会议记录
2. 按以下结构提取内容
3. 输出 Markdown 格式的总结

## 输出格式

### 会议摘要
- 用 2-3 句话概括会议主题和结论

### 关键决策
- 逐条列出已做出的决策，标注决策人

### 待办事项
| 事项 | 负责人 | 截止日期 |
|------|--------|----------|
| ... | ... | ... |

## 核心规则

- 待办事项必须可执行、可验证，避免"讨论一下"这种模糊表述
- 决策必须引用会议中的原话或明确依据
- 如会议未涉及某部分（如无决策），写"本次会议无此内容"，不要省略

## 不适用场景

- 会议涉及预算或资金审批 → 加载 `references/budget-compliance.md`
- 纯技术方案评审（无需待办提取） → 使用 `tech-review` Skill
- 非中文会议记录 → 当前仅支持中文，请使用其他工具

## 特殊情况

- 若会议涉及预算审批或资金决策，参照 `references/budget-compliance.md`
```

### references/budget-compliance.md

```markdown
# 资金合规检查

当会议涉及预算审批时，额外执行以下步骤：

1. 检查金额是否在审批人权限范围内
2. 标注是否需要财务部会签
3. 输出时增加「合规状态」字段

权限对照：
| 金额范围 | 审批层级 |
|----------|----------|
| < 10万 | 部门负责人 |
| 10-50万 | 事业部负责人 |
| > 50万 | CEO + 财务部 |
```
