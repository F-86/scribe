# ADR(架构决策记录)编写指南

## 定位

ADR(Architecture Decision Record)记录**一个**重要技术决策的始末:当时面临什么问题、考虑过哪些选项、为什么选了这个、带来什么后果。读者是贡献者和未来的自己——它的核心价值是**防止后人反复推翻**:几个月后有人问"这玩意儿当初为啥这么搞",ADR 给出答案。

与设计文档的边界见 [`doc-map.md`](doc-map.md):**ADR 记录单个决策(过去某刻),设计文档描述整体架构(当下现状)**。一条 ADR 只讲一个决策,一个项目会累积很多条。

## 关键约定

- **一决策一文件**,放 `docs/adr/` 或 `doc/adr/`
- 文件名带递增编号:`0001-use-postgresql.md`、`0002-adopt-event-sourcing.md`
- **ADR 不可变**:决策一旦记录就不改动内容。要推翻它,新建一条 ADR 并把旧的标记为"已被 ADR-NNNN 取代",保留历史轨迹
- 每条 ADR 有状态:`提议` → `已接受` / `已拒绝` → (后续可能)`已废弃` / `被取代`

## 结构模板(MADR 精简版)

```markdown
# ADR-0003: 采用 PostgreSQL 作为主数据库

> 状态:已接受 · 日期:2026-06-18 · 决策者:后端团队

## 背景与问题
我们需要一个主数据库,要求:支持事务、JSON 字段、全文检索,团队已有运维经验。
当前在 PostgreSQL 与 MongoDB 之间选择。

## 决策
采用 **PostgreSQL 15**。

## 理由
- 强事务保证,订单场景必需
- JSONB 兼顾结构化与灵活字段,无需引入第二个库
- 团队已有 PG 运维经验,降低学习与维护成本

## 备选方案
- **MongoDB**:文档模型灵活,但弱事务不满足订单一致性要求
- **MySQL**:成熟稳定,但 JSON 与全文检索能力弱于 PG

## 后果
- ✅ 单库满足结构化 + 半结构化需求,架构简单
- ⚠️ 水平扩展能力弱于 MongoDB,未来高并发需引入分库或读写分离(见未来工作)
```

## 编写原则

### DO ✅

- **背景写约束和当时的处境**:决策是在特定约束下做的,脱离背景的决策无法理解
- 后果要**同时写好的和坏的**——只写好处的 ADR 没说服力,也帮不到未来评估
- 备选方案写清"为什么没选",这往往比"为什么选"更有价值
- 编号 + 状态齐全,被取代时更新旧 ADR 的状态指向新编号
- 简短:一条 ADR 通常一页内,聚焦一个决策

### DON'T ❌

- 不要一条 ADR 塞多个决策——拆成多条
- 不要事后修改已接受 ADR 的决策内容——用新 ADR 取代,保留历史
- 不要记流水账式的小决策(变量命名、用哪个 lint 规则)——只记影响架构、难逆转、有争议的决策
- 不要省略备选方案——没有对比就看不出这个决策的分量

## 何时该写 ADR

```
✅ 值得记录:
- 选型决策(数据库、框架、消息队列、协议)
- 影响多个模块的架构模式(分层、事件驱动、微服务拆分)
- 难以逆转或迁移成本高的决策
- 有争议、团队讨论过的取舍

❌ 不用记录:
- 局部实现细节(某函数怎么写)
- 容易更改的决策(日志格式、配置项默认值)
- 显而易见、无备选的决策
```

## 通用规则

- **不虚构理由**:不清楚当时为什么这么定时,标 `<!-- TODO: 向 xxx 确认决策背景 -->`,不编造
- **优先从已有素材提取**:有 PR 讨论、设计文档、commit 说明时,从中还原决策背景
- **单一信息源**:决策始末在 ADR,整体架构在设计文档,二者互相链接而不重复
