# 提交信息(Commit Message)规范编写指南

## 定位

这类文档规定**一次 git 提交的信息怎么写**:格式、类型前缀、什么该写进正文。读者是所有向仓库提交的开发者。它的价值在于让提交历史可读、可检索、可自动生成 CHANGELOG。

落地形态通常是项目根目录的 `COMMIT_CONVENTION.md`,或 CONTRIBUTING.md 里的一节。边界见 [`doc-map.md`](doc-map.md):

| 文档 | 职责 |
|------|------|
| **提交信息规范** | 单次 commit 怎么写(格式、类型、范围) |
| **CONTRIBUTING** | 整体贡献流程(提交规范是其中一节,可链接到本规范) |
| **CHANGELOG** | 面向用户的版本变更摘要(由规范的提交聚合而来,但不是一回事) |

> 提交信息是写给**开发者和工具**的(逐条、技术视角);CHANGELOG 是写给**用户**的(聚合、影响视角)。两者不可互相替代。

## 结构模板

绝大多数项目采用 [Conventional Commits](https://www.conventionalcommits.org/),这是事实标准,**优先推荐**而非自创:

```markdown
# 提交信息规范

本项目遵循 [Conventional Commits](https://www.conventionalcommits.org/)。

## 格式

```
<类型>(<可选范围>): <简短描述>

<可选正文:解释“为什么”改,而非“怎么”改>

<可选脚注:Breaking Change、关联 issue>
```

## 类型

| 类型 | 用于 |
|------|------|
| `feat` | 新增功能 |
| `fix` | 修复 bug |
| `docs` | 仅文档改动 |
| `refactor` | 重构(不改行为) |
| `test` | 增改测试 |
| `chore` | 构建/工具/依赖等杂项 |
| `perf` | 性能优化 |

## 规则
- 简短描述用祈使句、现在时:“add”而非“added”;中文用“新增”而非“新增了”
- 首字母小写,结尾不加句号
- 范围(scope)标明影响模块:`feat(auth): 支持 OAuth 登录`
- 破坏性变更:在类型后加 `!`,或在脚注写 `BREAKING CHANGE: ...`
- 关联 issue 写脚注:`Closes #123`

## 示例
```
feat(parser): 支持解析数组类型配置

旧解析器遇到数组会报错。改用递归下降解析,
支持任意嵌套。

Closes #88
```
```

## 编写原则

### DO ✅

- **优先采用 Conventional Commits 等成熟标准**,不自创格式——工具链(语义化发版、自动 CHANGELOG)都围绕它
- 描述写**做了什么**,正文写**为什么**:diff 已经显示"怎么改",提交信息的价值在解释动机
- 给**真实的好/坏对照例子**——这是提交规范最有效的部分,开发者照着模仿
- 明确破坏性变更的标注方式(`!` 或 `BREAKING CHANGE`),这关系到版本号怎么跳
- 说明语言约定(英文还是中文描述)和时态,避免团队风格不一

### DON'T ❌

- 不要只给规则不给例子——抽象的"描述要清晰"没人能照做
- 不要把规范写得过于严苛导致没人遵守——抓核心(类型 + 简短描述 + 动机),细枝末节适度
- 不要和 CHANGELOG 规范混为一谈——提交是逐条原始记录,CHANGELOG 是面向用户的聚合摘要
- 不要遗漏破坏性变更的约定——这是提交信息里信息量最大的一类

## 章节取舍

| 章节 | 何时需要 | 何时可省 |
|------|---------|---------|
| 格式定义 | 始终 | 无 |
| 类型表 | 始终 | 无 |
| 范围(scope)约定 | 模块边界清晰的中大型项目 | 小项目可省 |
| 破坏性变更约定 | 对外发布、有版本号的项目 | 纯内部脚本 |
| 好/坏示例 | 始终(最有价值) | 无 |
| 与 CHANGELOG 的关系 | 同时维护 CHANGELOG 时 | 无 CHANGELOG |
| 工具/校验(commitlint、husky) | 想自动化约束 | 纯人工约定 |

## 通用规则

- **优先复用标准**:Conventional Commits、Angular 规范都是现成的,采用并按需裁剪,不凭空造一套
- **不虚构项目约定**:团队用英文还是中文、有无 scope 列表,不确定时标 `<!-- TODO: 确认 xxx -->`
- **单一信息源**:若项目已有 CONTRIBUTING,提交规范放一处,另一处链接过去,不重复两份
