# 部署 / 运维文档编写指南

## 定位

部署/运维文档回答:**怎么把这个系统跑到生产环境、出问题怎么处理?** 读者是运维人员(或负责部署的开发者)。它和 README 的"本地快速开始"不同——README 让人在本机跑起来体验,部署文档让人把它**稳定运行在生产环境**并能排障(边界见 [`doc-map.md`](doc-map.md))。

## 结构模板

```markdown
# 部署与运维

## 环境要求
| 项 | 要求 |
|----|------|
| 运行时 | Node.js 18+ |
| 数据库 | PostgreSQL 14+ |
| 内存 | 最低 2GB |
| 外部依赖 | Redis 6+(用于会话) |

## 配置项
所有配置通过环境变量注入:

| 变量 | 必填 | 默认 | 说明 |
|------|------|------|------|
| `DATABASE_URL` | 是 | - | PG 连接串 |
| `PORT` | 否 | 3000 | 服务端口 |
| `LOG_LEVEL` | 否 | info | 日志级别 |
| `JWT_SECRET` | 是 | - | 签名密钥,**勿提交进仓库** |

## 部署步骤
1. 准备环境变量(见上),写入 `.env` 或部署平台的 secret
2. 构建:`npm ci && npm run build`
3. 数据库迁移:`npm run migrate`
4. 启动:`npm run start`(生产用进程管理器,如 pm2 / systemd)

## 健康检查
- 存活探针:`GET /healthz` → 200
- 就绪探针:`GET /readyz` → 检查数据库连接

## 回滚
1. 切回上一镜像/版本:`...`
2. 如有破坏性迁移,先执行回滚迁移:`npm run migrate:down`

## 监控与日志
- 日志输出到 stdout,由平台采集
- 关键指标:请求延迟、错误率、数据库连接数

## 常见线上问题
见[故障排查](faq.md)或下方:
- **502**:服务未就绪,检查 `/readyz` 与数据库连接
- **内存持续增长**:检查 xxx
```

## 编写原则

### DO ✅

- **配置项用表格列全**:变量名、是否必填、默认值、说明——缺一不可,这是运维最常查的
- 标出**敏感配置**(密钥、密码)并强调"不要提交进仓库"
- 部署步骤可直接执行、有顺序,区分一次性步骤(迁移)和每次步骤(构建、启动)
- 必写**回滚方式**——上线会出错,没有回滚步骤的部署文档是不完整的
- 给健康检查端点,运维靠它接探针和负载均衡

### DON'T ❌

- 不要把密钥真实值写进文档——用占位符 + "从 xxx 获取"
- 不要假设环境——写清运行时、数据库、外部依赖的具体版本
- 不要只写"怎么启动"漏掉"怎么回滚/排障"——运维一半工作是处理异常
- 不要和 README 的本地开发说明混为一谈——生产部署有额外的安全和稳定性要求

## 章节取舍

| 章节 | 何时需要 | 何时可省 |
|------|---------|---------|
| 环境要求 | 始终 | 无 |
| 配置项 | 始终 | 无配置的极简工具 |
| 部署步骤 | 始终 | 无 |
| 回滚 | 有生产环境 | 纯本地工具 |
| 健康检查 | 长驻服务 | CLI / 一次性任务 |
| 监控与日志 | 生产服务 | 早期项目可简化 |
| 容器/编排(Docker/K8s) | 用容器部署 | 直接进程部署 |

## 通用规则

- **不虚构配置和命令**:不确定的环境变量、端口、命令标 `<!-- TODO: 确认 xxx -->`,不臆测
- **优先从已有素材提取**:有 `docker-compose.yml`、`.env.example`、CI 配置、部署脚本时,从中提取真实配置项
- **单一信息源**:线上排障细节可独立到[故障排查](faq.md),部署文档只链接
