# 项目级文档编排指南(初始化 / 补齐)

> 当用户的需求是**整个项目层面**的多文档处理(初始化一套文档、检查补齐缺失文档)时加载,而非写单独一份文档。

## 定位

这是一份**编排型**指南,不是又一种文档类型。它只负责回答"**这个项目该有哪些文档、现在缺哪些**",具体每份文档怎么写,仍交给对应的单类 L3(README → `readme.md`,CHANGELOG → `changelog.md`……)。

它覆盖两个场景,但用**同一套流程**:

| 场景 | 起点 | 信号 |
|------|------|------|
| **初始化** | 空项目(几乎全缺) | "我新建了个项目,帮我定规范"、"初始化项目文档" |
| **补齐** | 已有项目(部分缺) | "看看我项目缺哪些文档"、"补齐文档" |

两者的差别只在"现状"——初始化时现状几乎为空,补齐时已有一部分。流程完全一致。

## 统一流程

### 1. 确定项目类型

问一句,用于裁剪推荐集:

> 这个项目是什么类型?库/SDK、服务/应用、CLI 工具,还是内部工具?是否开源?

### 2. 扫描现状

用 Glob / LS 扫**项目根目录的顶层文档**,看已有哪些:`README*`、`AGENTS.md`/`CLAUDE.md`、`CHANGELOG*`、`CONTRIBUTING*`、`PROGRESS*`/`ROADMAP*`、`LICENSE*`、`SECURITY*`、`.github/`、提交规范(`COMMIT_CONVENTION*` 或 CONTRIBUTING 内的提交节)。

> 只扫顶层文档,**不递归遍历整个代码库**——这是轻量、有界的检查。初始化场景通常扫出"几乎全无"。

### 3. 算出推荐集与缺口

**推荐集 = 通用基础集 + 该类型的附加项**;**缺口 = 推荐集 − 现状**。

#### 通用基础集(任何项目都推荐,与类型无关)

| 文档 | 为什么通用 |
|------|-----------|
| README | 任何项目的门面 |
| AGENTS.md / CLAUDE.md | AI agent 开发的标配上下文 |
| 提交规范(Conventional Commits) | 任何用 git 的项目都适用 |
| CHANGELOG | 任何会迭代、有版本的项目 |
| PROGRESS | 追踪"要做什么、做到哪了" |

#### 类型附加项(在基础集之上追加)

| 项目类型 | 追加 |
|---------|------|
| 库 / SDK | API 参考文档 |
| 服务 / 应用 | 部署 / 运维文档 |
| CLI 工具 | (通常无附加) |
| 内部工具 | (通常无附加) |
| **开源**(任意类型叠加) | LICENSE + CONTRIBUTING + SECURITY + 治理小文档(Issue/PR 模板) |

> 推荐集的依据是 [`doc-map.md`](doc-map.md) 的「成熟度分阶段」表——起步期不必铺满,优先通用基础集,成熟后再加设计文档/ADR/FAQ 等。

### 4. 列清单交用户确认(关键)

**不自动生成。** 把缺口列成清单,标明每项的作用,让用户勾选要补哪些:

```markdown
检测到这是一个【开源的库】。建议补齐以下文档(已有的已排除):

基础:
- [ ] README —— 项目门面与上手
- [ ] AGENTS.md —— AI agent 开发上下文
- [ ] 提交规范 —— 统一 commit 格式
- [ ] CHANGELOG —— 版本变更记录

库 + 开源追加:
- [ ] API 参考 —— 对外接口文档
- [ ] LICENSE / CONTRIBUTING / SECURITY

请告诉我补哪些(可全选,也可只挑几个)。
```

用户确认后才进入生成。**用户可去掉任何一项,scribe 不强加。**

### 5. 逐个生成

对用户确认的每一项,加载其单类 L3 逐个生成(遵循 SKILL.md「多个文档逐个处理,不一次性输出多份」的规则)。每份生成时仍需收集该文档所需的上下文。

**生成顺序**:按"被依赖在前"排序,避免先生成的文档引用到还不存在的文件——
1. 先 **README、AGENTS.md/CLAUDE.md** —— 承载项目背景(名称、用途、技术栈),后续文档可复用这些信息
2. 再 **CONTRIBUTING、提交规范、LICENSE、SECURITY** 等规范/治理类
3. 最后 **API 参考、部署、设计文档** 等依赖前述背景的专项文档
4. README 里指向其他文档的导航链接(如「文档」节),在相关文件都生成后再回填

> 顺序是建议而非强制:若某文档要链接尚未生成的文件,先留占位、最后统一回填即可。

## 编写原则

### DO ✅

- **先确认再生成**:无论初始化还是补齐,都先列清单等用户拍板
- **按类型裁剪**:CLI 工具不强推 API 参考,非开源不强推 LICENSE/SECURITY
- **复用单类 L3**:本指南只做编排,每份文档的写法以对应单类 L3 为准
- **排除已有**:补齐场景把现状里已存在的排除掉,只提缺的

### DON'T ❌

- 不要一次性把 14 类文档全铺给项目——只推荐当前阶段需要的
- 不要生成空模板占位——用户没确认的不建,确认的也要填真实上下文
- 不要替用户决定补哪些——列选项,由用户勾选
- 不要为了"补齐"而把内容硬塞进不合适的文档(参考 doc-map 的边界)

## 通用规则

- **不虚构项目信息**:生成各文档时,不确定的内容用 `<!-- TODO -->` 标注
- **单一信息源**:多份文档间有重叠内容时(如提交规范 vs CONTRIBUTING),按 doc-map 的边界各放一处、互相链接
- **与 doc-map 配合**:本指南决定"该有哪些",doc-map 决定"各管什么、边界在哪",两者配合使用
