# 测试文档编写指南

## 定位

测试文档回答「这个项目**怎么测、测了什么、怎么写测试**」。它有三种形态,读者和写法都不同,动笔前先分清(与相邻文档的边界见 [`doc-map.md`](doc-map.md)):

| 形态 | 读者 | 回答 | 组织方式 |
|------|------|------|---------|
| **测试用例规格** | QA / 测试人员 / 评审者 | "这个功能要测哪些场景、每个怎么测、期望什么结果" | 逐条用例:前置 → 步骤 → 预期 |
| **测试策略 / 计划** | 团队 / 维护者 | "项目整体怎么测——分几层、覆盖率目标、范围与不测什么、CI 怎么跑" | 分主题的说明文 |
| **测试编写指南** | 贡献者 | "我要加测试,该放哪、怎么命名、用什么断言、怎么 mock、怎么跑" | 约定 + 命令 + 示例 |

> 三者**默认各自独立成文**(`TEST_PLAN.md`、`TESTING.md`、`test-cases/`),职责更清晰、便于各自的读者直接找到。仅当项目极小、内容只有寥寥几条时,才考虑把某一形态并入相邻文档(如把"怎么写测试"并进 CONTRIBUTING 的「测试」一节)。先确认有对应读者再决定写哪几种,但不必为了"省文件"而强行合并。

---

## 一、测试用例规格

逐条记录"测什么、怎么测、期望什么"。给手工执行或评审用;自动化测试已覆盖的部分通常不必再写一份纸面用例(代码即用例),用例规格的价值在**自动化难覆盖或需人工判断**的场景(交互流程、兼容性矩阵、验收标准)。

### 结构模板

```markdown
# {模块/功能} 测试用例

## TC-001 用户登录成功

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **前置条件** | 已有账号 alice / 密码正确;未登录状态 |
| **测试步骤** | 1. 打开登录页<br>2. 输入用户名 alice、正确密码<br>3. 点击「登录」 |
| **预期结果** | 跳转到首页,右上角显示用户名 alice |
| **实际结果** | <!-- 执行时填写 --> |

## TC-002 密码错误时拒绝登录

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **前置条件** | 已有账号 alice;未登录状态 |
| **测试步骤** | 1. 打开登录页<br>2. 输入 alice + 错误密码<br>3. 点击「登录」 |
| **预期结果** | 停留在登录页,提示「用户名或密码错误」,不泄露是哪一项错 |
```

简单场景也可用表格平铺(一行一条用例):用例 ID | 标题 | 前置 | 步骤 | 预期 | 优先级。

### 编写原则

**DO ✅**
- **一条用例只验一个点**:成功登录和密码错误拆成两条,别塞进一条
- **预期结果可判定**:写"显示用户名 alice"而非"显示正确"——执行者要能明确判断通过/失败
- **覆盖正常 + 异常 + 边界**:正常路径、错误输入、边界值(空、超长、0、最大值)都要有用例
- **标优先级**:P0(核心流程,必过)/ P1 / P2,资源有限时先跑高优先级
- **用例 ID 稳定**:`TC-001` 这类编号一旦分配不复用,方便缺陷关联和回归追踪

**DON'T ❌**
- 不要写"测试登录功能是否正常"这种笼统用例——拆成具体场景
- 不要把已被自动化测试稳定覆盖的细节再抄一份纸面用例(维护双份,易不同步)
- 不要省略前置条件——少了它用例无法复现

## 二、测试策略 / 计划

讲清项目**整体怎么测**,让团队对齐、新人快速了解测试体系。

### 结构模板

```markdown
# 测试策略

## 测试分层
- **单元测试**:函数/类级别,占比最高,跑得最快(`npm run test:unit`)
- **集成测试**:模块间协作、数据库/外部服务交互(`npm run test:integration`)
- **端到端(E2E)**:模拟真实用户操作完整流程(`npm run test:e2e`)

> 遵循测试金字塔:单元多、集成中、E2E 少。

## 覆盖率目标
- 整体行覆盖 ≥ 80%,核心模块(支付、认证)≥ 95%
- 覆盖率由 CI 强制,低于阈值阻断合并

## 测试范围
- **测**:业务逻辑、API 契约、关键用户路径、错误处理
- **不测**:第三方库内部、纯配置、自动生成的代码 —— 明确写出"不测什么"同样重要

## 测试数据与环境
- 单元测试用内存数据库;集成测试用 docker-compose 起依赖
- 测试数据通过 fixtures/factory 生成,不依赖生产数据

## CI 中的测试
- 每个 PR 自动跑单元 + 集成;E2E 在合并到 main 后跑
- 测试失败阻断合并
```

### 编写原则

**DO ✅**
- **明确分层与各层职责**:说清单元/集成/E2E 各测什么、各自的命令
- **写出"不测什么"**:范围边界和"测什么"同等重要,避免无谓投入和覆盖率焦虑
- **覆盖率目标要落地**:给具体数字 + 是否 CI 强制,而非"尽量高"
- **链接到 CI 配置**:策略是说明,真实门禁在 CI 里,指过去而非抄一遍

**DON'T ❌**
- 不要写成"我们重视质量"这类口号——要可执行的分层、命令、阈值
- 不要和"测试编写指南"混为一谈:策略讲**测什么/测到什么程度**(规划),编写指南讲**怎么动手写**(操作)

## 三、测试编写指南

给贡献者照着写测试的操作手册。这一形态与 CONTRIBUTING 的「测试要求」高度相关——见下方边界。

### 结构模板

```markdown
# 如何编写测试

## 测试放在哪
- 单元测试与源码同目录:`foo.ts` → `foo.test.ts`
- 集成/E2E 集中放 `tests/integration/`、`tests/e2e/`

## 命名约定
- 测试文件:`*.test.ts`
- 用例描述用「行为」句式:`it('密码错误时返回 401')`,不要 `it('test login')`

## 怎么跑
```bash
npm test                 # 全部
npm test -- foo.test.ts  # 单个文件
npm run test:watch       # 监听模式
```

## 断言与 mock
- 断言库:Vitest 的 `expect`
- 外部 HTTP 用 `msw` mock,不要真实联网
- 时间相关用 `vi.useFakeTimers()`,不要 sleep

## 写一个测试的示例
```ts
import { describe, it, expect } from 'vitest'
import { login } from './auth'

describe('login', () => {
  it('密码正确时返回 token', async () => {
    const res = await login('alice', 'correct')
    expect(res.token).toBeDefined()
  })

  it('密码错误时抛出 401', async () => {
    await expect(login('alice', 'wrong')).rejects.toThrow('401')
  })
})
```
```

### 编写原则

**DO ✅**
- **可执行命令优先**:写 `npm test -- foo.test.ts`,而非"运行对应测试"
- **给一个能照抄的真实示例**:贡献者照着改最快
- **约定要具体**:文件放哪、怎么命名、用哪个断言库/mock 工具,逐条写明
- **从已有测试提取风格**:项目已有测试时,让新测试与之一致,而非另立一套

**DON'T ❌**
- 不要罗列测试框架的完整 API——那是框架文档的事,这里只写**本项目的约定**
- 不要和测试策略重复:这里不讲覆盖率目标和分层规划,只讲怎么动手写

## 章节取舍

| 内容 | 何时需要 | 何时可省 |
|------|---------|---------|
| 测试用例规格 | 有专门 QA、验收测试、高可靠性要求 | 纯自动化测试覆盖的项目(代码即用例) |
| 测试策略 / 计划 | 多人协作、有分层测试体系、CI 门禁 | 个人小项目 |
| 测试编写指南 | 接受外部贡献、希望测试风格统一 | 无外部贡献者 |
| 覆盖率目标 | 团队对质量有量化要求 | 起步期原型 |
| "不测什么"范围 | 始终建议——划清边界 | 无 |
> 三种形态按需取用,不必都写——先确认有对应读者。但默认**独立成文**:有了读者就给它独立文件,职责清晰、好找好维护。只有项目极小、整块测试内容只有寥寥几条时,才并入 CONTRIBUTING 的「测试」一节(参考 [`doc-map.md`](doc-map.md) 的成熟度分阶段)。

## 通用规则

- **来自真实测试体系**:命令、目录、框架要与项目实际一致,不虚构。不清楚时问用户或定向查看现有测试文件,不全库遍历
- **可执行 > 抽象**:写具体命令、具体断言,而非"进行测试""验证功能"
- **单一信息源**:测试相关内容若已在 CONTRIBUTING / 设计文档 / CI 配置中,链接过去,不复制
- **优先从已有素材提取**:项目已有测试目录、CI 配置、测试框架时,从中提炼约定,保持风格一致
