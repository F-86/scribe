# 治理小文档编写指南

## 定位

这类是 GitHub 生态里**短小、强模板化**的治理文档,规范协作行为。读者是贡献者与社区成员。它们各自职责单一,边界见 [`doc-map.md`](doc-map.md):

| 文档 | 位置 | 职责 |
|------|------|------|
| **Issue 模板** | `.github/ISSUE_TEMPLATE/` | 引导提报者提供必要信息 |
| **PR 模板** | `.github/pull_request_template.md` | 引导提交者说明改动与自检 |
| **CODE_OF_CONDUCT.md** | 根目录或 `.github/` | 社区行为准则与违规处理 |

> 与 CONTRIBUTING 的区别:CONTRIBUTING 讲"怎么贡献"(流程、规范),这些模板是贡献时**当场填的表单**;行为准则讲"如何相处",不是技术流程。

## 一、Issue 模板

GitHub 支持按类型分多个模板。最常见是 Bug 报告和功能请求。

### Bug 报告模板

```markdown
---
name: Bug 报告
about: 报告一个问题,帮助我们改进
labels: bug
---

## 问题描述
<清晰描述发生了什么>

## 复现步骤
1. 进入 '...'
2. 点击 '...'
3. 看到错误

## 预期行为
<你期望发生什么>

## 实际行为
<实际发生了什么,附报错原文/截图>

## 环境
- 版本:
- 操作系统:
- 其他相关信息:
```

### 功能请求模板

```markdown
---
name: 功能请求
about: 提议一个新功能
labels: enhancement
---

## 要解决的问题
<你遇到了什么困扰?>

## 期望的方案
<希望怎么解决>

## 备选方案
<考虑过的其他做法>
```

## 二、PR 模板

```markdown
## 改动说明
<这个 PR 做了什么,为什么>

## 关联 Issue
Closes #

## 改动类型
- [ ] Bug 修复
- [ ] 新功能
- [ ] 文档
- [ ] 重构(无行为变更)

## 自检清单
- [ ] 已自测,功能符合预期
- [ ] 已补充/更新测试
- [ ] 已更新相关文档
- [ ] 遵循项目代码规范
```

## 三、CODE_OF_CONDUCT.md

行为准则**强烈建议直接采用成熟标准**——[Contributor Covenant](https://www.contributor-covenant.org/) 是事实标准,无需自创。

```markdown
# 贡献者行为准则

本项目采用 [Contributor Covenant](https://www.contributor-covenant.org/version/2/1/code_of_conduct/) 2.1 版作为行为准则。

## 我们的承诺
为营造开放友好的环境,我们承诺...(采用标准文本)

## 举报
如遇违规行为,请联系 <conduct@example.com>。所有投诉都会被审查和调查。
```

## 编写原则

### DO ✅

- **模板即表单**:每个字段都是为了"拿到处理问题必需的信息",不多问
- Bug 模板必含:复现步骤 + 预期/实际 + 环境——缺一个就难定位
- PR 模板含自检清单,把 reviewer 要反复确认的事前移给提交者
- 行为准则用 Contributor Covenant,只改联系邮箱,不自己造措辞
- 用 YAML frontmatter 设 `name`/`about`/`labels`,GitHub 会自动渲染选择界面

### DON'T ❌

- 不要把模板做得太长——字段越多,提报者越可能放弃或乱填
- 不要要求填用户拿不到的信息(如内部错误码)
- 不要自创行为准则措辞——法律和社区共识问题用成熟标准更稳妥
- 不要把 CONTRIBUTING 的完整流程塞进 PR 模板——模板只放当场要勾的清单

## 章节取舍

| 文档 | 何时需要 | 何时可省 |
|------|---------|---------|
| Bug / 功能 Issue 模板 | 接受外部 issue 的项目 | 私有/内部项目 |
| PR 模板 | 接受外部 PR | 单人项目 |
| CODE_OF_CONDUCT | 开源、有社区互动 | 内部工具 |

## 通用规则

- **不虚构联系方式/流程**:邮箱、处理流程不确定时标 `<!-- TODO: 填写 xxx -->`
- **优先复用标准**:行为准则、模板都有成熟模板,优先采用再裁剪
- **保持精简**:治理小文档的价值在"低门槛",越短越好
