# SECURITY.md 编写指南

## 定位

SECURITY.md 回答一个问题:**发现安全漏洞该怎么上报?** 读者是安全研究者和用户。它的核心是给出一条**私密的上报渠道**和明确的响应预期,避免漏洞被公开披露(public issue)而被恶意利用。

GitHub 会自动识别根目录或 `.github/` 下的 `SECURITY.md`,在仓库"Security"页展示。边界见 [`doc-map.md`](doc-map.md):它只管安全上报,不讲功能怎么用。

## 结构模板

```markdown
# 安全策略

## 支持的版本

下列版本会接收安全更新:

| 版本 | 是否支持 |
|------|---------|
| 2.x | ✅ |
| 1.x | ✅(仅安全修复,至 2026-12) |
| < 1.0 | ❌ |

## 上报漏洞

**请勿通过公开 issue 上报安全漏洞。**

请通过以下方式私密上报:
- 邮件:<security@example.com>
- 或使用 GitHub 的 [私密漏洞上报](https://docs.github.com/code-security/security-advisories)

上报时请尽量包含:
- 漏洞类型与影响范围
- 复现步骤或 PoC
- 受影响的版本

## 响应流程

- **3 个工作日内**:确认收到
- **7 个工作日内**:初步评估,告知是否受理及严重程度
- 修复后会发布安全公告,并在你同意的前提下致谢

## 披露政策
我们采用协调披露:修复发布前请勿公开细节。修复后 {N} 天公开漏洞详情。
```

## 编写原则

### DO ✅

- **第一要务是私密渠道**:醒目地写明"不要用公开 issue",给出邮箱或 GitHub 私密上报入口
- 给**明确的响应时间承诺**(确认收到、初步评估),哪怕是"尽力而为"也要写——研究者最怕石沉大海
- 用表格写清**哪些版本还在接收安全更新**,旧版本用户才知道是否需要升级
- 说明上报应包含什么(影响、复现、版本),提高一次上报的有效性
- 写明致谢/披露政策,鼓励负责任的披露

### DON'T ❌

- 不要只留一个公开 issue 链接——那等于让漏洞公开暴露
- 不要承诺做不到的响应时间——写不准就用"尽快"并说明无 SLA
- 不要把它写成免责声明——它是给研究者的协作指引,不是法律文书
- 不要遗漏支持版本表——用户无法判断自己的版本是否还安全

## 章节取舍

| 章节 | 何时需要 | 何时可省 |
|------|---------|---------|
| 上报渠道 | 始终(核心) | 无 |
| 支持的版本 | 有多个维护版本 | 只有一个版本 |
| 响应流程/时间 | 强烈建议 | 个人小项目可简化为"尽快回复" |
| 披露政策 | 有正式安全流程 | 早期项目可省 |
| 致谢/名人堂 | 想激励上报 | 可省 |

## 通用规则

- **不虚构联系方式和 SLA**:邮箱、响应时间不确定时标 `<!-- TODO: 填写安全联系邮箱 -->`,绝不编一个不存在的邮箱
- **优先复用平台能力**:GitHub 私密漏洞上报、Security Advisories 是现成的,优先引导用户用
- **单一职责**:只讲安全上报,功能问题引导到 issue/FAQ
