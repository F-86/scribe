# 文档职责总览(文档地图)

> 横切所有文档类型的总纲。其他 `references/*.md` 回答「某一类文档**怎么写**」,本文件回答「**该写哪一类、各类边界在哪**」。
>
> 何时加载:用户说不清要写哪种文档、或两类文档边界模糊(该写 README 还是设计文档?该记进 CHANGELOG 还是 PROGRESS?)时,加载本文件辅助选型。

## 定位

每份文档都该有**单一、清晰的职责**。文档之间最常见的问题不是缺失,而是**职责重叠**——同一件事写进多处,维护时不同步,读者无所适从。本文件给出每类文档"管什么、不管什么"的边界,作为所有单类规范边界声明的单一信息源。

判断一份内容该放哪里,先问三件事:**写给谁看(读者)** → **回答什么时间的问题(过去/现在/未来)** → **回答什么问题**。

## 文档职责总表

| 文档 | 读者 | 时间视角 | 回答什么 | **不负责什么** |
|------|------|---------|---------|--------------|
| **README** | 使用者 / 初次接触者 | 当下 | 这是什么、能干什么、怎么快速跑起来 | 为什么这么设计(→设计文档)、改了什么(→CHANGELOG) |
| **CLAUDE.md / AGENTS.md** | AI agent | 当下 | 项目约定、命令、风格,让 agent 正确协作 | 给人读的介绍(→README) |
| **SKILL.md** | AI agent | 当下 | 一个 skill 的能力、触发条件、操作流程 | 通用项目说明(→README) |
| **API 文档** | 集成方开发者 | 当下 | 接口怎么调、参数/返回/错误 | 内部实现、为什么这么设计 |
| **CONTRIBUTING.md** | 贡献者 | 当下 | 怎么提 PR、规范、测试要求 | 架构原理(→设计文档) |
| **CHANGELOG** | 升级用户 | 过去(已发布) | 每个版本改了什么、有无破坏性变更 | 还没做的计划(→PROGRESS) |
| **PROGRESS.md** | 维护者 / 协作者 | 现在 + 未来 | 要做什么、做到哪了、分几个阶段 | 已发布版本的逐条变更(→CHANGELOG) |
| **设计文档 / 架构文档** | 贡献者 | 当下(原理) | 系统为什么这么设计、模块如何划分、关键权衡 | 怎么用(→README)、单个决策始末(→ADR) |
| **ADR(架构决策记录)** | 贡献者 / 未来的自己 | 过去(决策当时) | 某个技术选型当时为什么这么定、备选与后果 | 系统整体架构(→设计文档) |
| **SECURITY.md** | 安全研究者 / 用户 | 当下 | 漏洞如何上报、支持的版本、响应流程 | 功能怎么用(→README) |
| **部署 / 运维文档** | 运维 | 当下 | 环境依赖、配置项、上线步骤、线上排障 | 本地开发上手(→README/CONTRIBUTING) |
| **FAQ / 故障排查** | 使用者 | 当下 | 常见疑问的答案、报错的排查步骤 | 完整功能说明(→README/API 文档) |
| **提交信息规范** | 贡献者 | 当下 | 单次 commit 怎么写(格式、类型、范围) | 贡献全流程(→CONTRIBUTING)、面向用户的变更摘要(→CHANGELOG) |

## 易混边界澄清

最容易写串的几对文档,分工如下:

- **PROGRESS vs CHANGELOG** —— 时间视角不同。PROGRESS 朝前看(要做什么、做到哪了),CHANGELOG 朝后看(已发布版本改了什么)。一个任务做完且发布后,它在 PROGRESS 里标记 `✅`,其**用户可见的变更**才写进 CHANGELOG。PROGRESS 的"已完成"是计划里程碑,不是逐条变更流水。
- **README vs 设计文档** —— README 回答"我是用户,怎么用你";设计文档回答"我是开发者,系统为什么长这样"。架构细节塞进 README 会让它又长又劝退。
- **设计文档 vs ADR** —— 设计文档描述**整体**架构现状(模块、数据流、依赖);ADR 记录**单个**决策的始末(背景→选项→定哪个→后果)。一份设计文档,背后可能有多条 ADR 支撑。
- **FAQ vs 故障排查** —— FAQ 回答"常见疑问"(这功能支持 X 吗?);故障排查回答"出错了怎么办"(报这个错该怎么查)。两者都可独立成文,小项目也可并入 README。
- **README vs CONTRIBUTING** —— README 给使用者(怎么装、怎么用);CONTRIBUTING 给贡献者(怎么改、怎么提 PR)。
- **CLAUDE.md/AGENTS.md vs README** —— 前者给 AI agent(项目约定、命令);后者给人(介绍、上手)。目录结构说明属于 README,agent 文件不必重复。
- **提交信息规范 vs CHANGELOG** —— 提交信息是逐条原始记录,给开发者和工具看(技术视角);CHANGELOG 是面向用户的聚合摘要(影响视角)。前者是后者的素材,但不能互相替代。
- **提交信息规范 vs CONTRIBUTING** —— 提交规范只管"一次 commit 怎么写";CONTRIBUTING 管整个贡献流程。项目同时有两者时,规范放一处,另一处链接,不重复两份。

## 选型决策:想记录 X,该写哪份?

| 你想记录的东西 | 写进 |
|--------------|------|
| 项目是什么、怎么用 | README |
| 接口怎么调 | API 文档 |
| 这版改了什么(已发布) | CHANGELOG |
| 接下来要做什么、做到哪了 | PROGRESS.md |
| 为什么选了方案 A 而不是 B | ADR |
| 系统整体怎么搭的 | 设计文档 |
| 怎么提 PR、代码规范 | CONTRIBUTING.md |
| 怎么部署、配置项有哪些 | 部署/运维文档 |
| 发现漏洞怎么上报 | SECURITY.md |
| 用户老问的问题 / 常见报错 | FAQ / 故障排查 |
| 让 AI agent 遵守的项目约定 | CLAUDE.md / AGENTS.md |
| 每次 commit 信息怎么写 | 提交信息规范 |

## 成熟度:分阶段补,别一次铺满

文档是分阶段长出来的。盲目铺一堆空模板比没有更糟——读者会被过期/空洞的内容误导。

```
起步期:  README + LICENSE
成长期:  + CONTRIBUTING + CHANGELOG + 基础 API 文档 + PROGRESS
成熟期:  + 设计/架构文档 + ADR + 部署/运维 + SECURITY + FAQ
```

判断该不该新增一份文档:**先确认有对应的读者群、且现有文档无法承载这部分内容**。否则先并入已有文档(如 FAQ 并入 README),等内容长大了再独立。

## 通用规则

- **单一职责优先**:一份内容只在一处是"信息源",其他地方需要时链接过去,不复制。
- **边界声明指向本文件**:各单类规范若要说明与相邻文档的边界,统一引用本文件,不各自重述。
- **按读者裁剪**:没有对应读者的文档不写;读者能从已有文档找到答案的内容不另起一份。
