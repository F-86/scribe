# 修改文档操作指南

> 仅当用户要求修改、规范、重构、审查现有文档时加载。新建文档的流程在 SKILL.md L2 中。

## 修改模式识别

根据用户意图确定修改策略：

| 模式 | 典型信号 | 策略 |
|------|---------|------|
| **局部修改** | "这里改一下"、"把 xxx 换成 yyy"、"加上 xxx"、"删掉 xxx" | 精准修改，不动其他部分 |
| **规范化** | "规范一下"、"按标准改"、"统一格式"、"格式不统一" | 对照 L3 规范逐项检查修正 |
| **重构** | "重构"、"重新组织"、"结构太乱了"、"太长了拆一下" | 保持内容，重排结构 |
| **审查** | "review 一下"、"看看哪里有问题"、"检查"、"帮我看看"、"错了"、"不太对" | 先诊断问题，列出清单 |

## 修改步骤

### A. 识别文档类型和 agent 环境

**在执行修改前，必须先识别文档类型和 agent 环境。** 这一步不能跳过。

根据文件路径或内容判断文档类型：

| 文档类型 | 识别方式 |
|---------|---------|
| `CLAUDE.md` / `AGENTS.md` | 文件名通常是 `CLAUDE.md`、`AGENTS.md`、`rules.md` 或 `.claude/`、`.codex/` 下的指令文件 |
| `SKILL.md` | 文件名通常是 `SKILL.md`，位于 skill 目录下 |
| `README` | 文件名通常是 `README.md` |
| `CONTRIBUTING.md` | 文件名通常是 `CONTRIBUTING.md` |
| `CHANGELOG` | 文件名通常是 `CHANGELOG.md` |
| `PROGRESS.md` | 文件名通常是 `PROGRESS.md`、`ROADMAP.md`、`TODO.md` |
| API 文档 | 文件名通常是 `API.md`、`openapi.yaml`/`.json`、`swagger.*`，或 `docs/` 下的接口文档 |
| 设计 / 架构文档 | 文件名通常是 `DESIGN.md`、`ARCHITECTURE.md`、`RFC-*.md`，或 `docs/` 下的设计文档 |
| ADR | 文件名通常是 `docs/adr/NNNN-*.md`，带递增编号 |
| `SECURITY.md` | 文件名通常是 `SECURITY.md`，位于根目录或 `.github/` |
| 部署 / 运维文档 | 文件名通常是 `DEPLOY.md`、`DEPLOYMENT.md`、`docs/ops.md` |
| FAQ / 故障排查 | 文件名通常是 `FAQ.md`、`TROUBLESHOOTING.md` |
| 治理小文档 | 文件名通常在 `.github/`（Issue/PR 模板）或 `CODE_OF_CONDUCT.md` |

若无法确定类型，向用户确认。

**当文档类型是 SKILL.md 时**，额外确认目标 agent：

> 这个 skill 是给哪个 agent 用的？pi、Claude Code、还是 Codex？

| 目标 agent | 加载的规范 |
|-----------|----------|
| 不确定 / 多 agent | 仅 `skill-spec.md`（通用规范） |
| pi | `skill-spec.md` + `skill-pi.md` |
| Claude Code | `skill-spec.md` + `skill-claude.md` |

### B. 读取文档

加载用户指定的文档。如果用户没指定路径，先问清楚。

### C. 加载对应规范

根据步骤 A 识别的文档类型，加载对应的 L3 参考指南。具体的类型→文件映射见 SKILL.md L2 第 4 步的表格。

### D. 诊断问题

对照规范，从以下维度检查文档：

| 维度 | 检查项 |
|------|--------|
| **结构** | 必备章节是否缺失？章节顺序是否合理？层级嵌套是否正确？ |
| **L1/L2/L3 分层**（SKILL.md） | L1 是否过重？L2 是否过轻？L3 内容是否误放？ |
| **格式** | 代码块是否标注语言？列表缩进是否一致？标题层级是否跳级？ |
| **内容** | 是否有空泛表述（"强大的"、"灵活的"）？命令是否可执行？是否有 TODO 残留？ |
| **受众** | 内容是否适合目标受众？是否有对受众无价值的章节？ |

将发现的问题归纳为清单，每条标注**严重程度**和**修改建议**：

```markdown
## 诊断结果

### 🔴 严重（与规范冲突）
- [ ] L1 description 包含触发条件，应拆到 L2 —— 建议只保留核心定位 + 关键词
- [ ] 缺少「不适用场景」章节 —— 建议新增独立章节

### 🟡 改进（偏离最佳实践）
- [ ] 标题层级跳级（## 直接到 ####）—— 建议补 ###
- [ ] 多处"强大的""灵活的"空泛形容 —— 建议用具体特性替代

### 🟢 建议（锦上添花）
- [ ] README 缺少徽章 —— 建议添加 CI / license 徽章
```

### E. 用户确认

**不要直接修改**。先展示诊断结果，询问用户：

> 以上是我发现的问题。请确认哪些需要修改？可以直接说"全部改"，也可以只选其中几项。

### F. 执行修改

用户确认后，逐项修改。每条修改说明：
1. 改了什么（引用具体位置）
2. 为什么改（引用规范的哪一条）

### G. 审阅

修改后再次让用户确认，与新建流程的最后一步相同。

## 核心规则

- **先诊后治**：修改前必须先诊断并列出问题，获得用户确认后再改。不要看到问题就动手
- **最小改动**：只改有问题的部分，保留正确的部分。不重写整份文档除非用户明确要求
- **每改必解释**：每条修改都要说明依据，指向 L3 规范的具体条款
- **不推断意图**：不确定用户想怎么改时，提出选项让用户选择，而非自行判断
