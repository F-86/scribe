# ADR-0003: 设立 doc-map.md 作为文档职责的单一信息源

> 状态:已接受 · 日期:2026-06-18 · 决策者:项目维护者

## 背景与问题

scribe 覆盖的文档类型越来越多,"哪类文档管什么、与相邻文档的边界在哪"成了反复出现的问题:PROGRESS 与 CHANGELOG、README 与设计文档、FAQ 与故障排查……这些边界声明若分散写在各自的 L3 指南里,会出现两个问题:(1) 同一对边界在两份文件里各说一次,易不一致;(2) 当用户"说不清要写哪种文档"时,没有一个统一的地方供 agent 查阅选型。

## 决策

新增 `references/doc-map.md` 作为**横切所有文档类型的职责总览**,集中放置:文档职责总表、易混边界澄清、选型决策、成熟度分阶段。各单类 L3 指南若需说明边界,统一**链接**到 doc-map,不各自重述。L2 在"识别文档类型"环节,遇类型不清或边界模糊时加载它。

## 理由

- **单一信息源**:边界只在一处定义,消除不一致
- **服务选型**:给 agent 一个明确的"该写哪类"决策依据,而非散落各处
- **双读者**:同样适合人读,README 可直接链接它作为"scribe 覆盖哪些文档"的总说明

## 备选方案

- **边界分散在各 L3**:每份指南自己写与邻居的边界。维护时易漂移、互相矛盾,且无法服务"选型"场景,否决。
- **把职责表放进 SKILL.md L2**:会让 L2 变重,违背三层架构(L2 只放识别 + 路由指针),否决。

## 后果

- ✅ 文档边界有唯一权威出处,各 L3 引用它即可
- ✅ 用户犹豫"写哪种"时,agent 有据可依
- ⚠️ doc-map 本身需随新增文档类型同步更新,成为又一处需维护的接入点
